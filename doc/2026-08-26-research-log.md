## Repository workflow and H4rmony SFT planning

The local checkout was fast-forwarded to repository commit
`613693f414ddd105149d694ecc66b17bf7b5a02f`, which includes the August 25
H4rmoniousCaramel matched-checkpoint pilot. A repository-level `AGENTS.md` was
added to make two working conventions persistent for future sessions: completed
task changes should be committed unless the user explicitly opts out, and
substantive work should be recorded in the dated research log in the same commit.

The H4rmony source dataset supplies three ranked completions for each prompt. R1
is the preferred, most environmentally aligned response; R2 is the ambivalent
response; and R3 is the least environmentally aligned response. The pairwise
source rows compare R1 with R2 and R1 with R3. The proposed SFT intervention uses
only one R1 completion per prompt; “R1” does not refer to the DeepSeek-R1 model.

The H4rmony project's public `data/train.csv` contains 517 SFT rows covering 512
unique prompts. Five prompts occur twice. The target outputs are short, averaging
about 123 characters, so the R1-only corpus is a very small SFT run.

For one R1 completion per unique H4rmony prompt, a dense 8B base model, LoRA rank
16, three epochs, BF16, gradient checkpointing, dynamic padding or sequence
packing, and a single A100, the revised provisional estimate is:

- roughly 3–10 minutes of optimization for two or three epochs; and
- approximately 15–35 minutes end to end once model download, tokenization,
  evaluation, and adapter saving are included, with up to 45 minutes budgeted for
  a cold or slower Colab session.

These are planning ranges rather than measured benchmarks. Before the full run,
the R1-only dataset should be deduplicated by prompt, tokenized with the exact
base tokenizer, and its mean, p95, and maximum sequence lengths recorded. A short
timed training sample should then replace the provisional estimate with measured
tokens per second. Because the completions are short, model loading and evaluation
may take longer than optimization itself.

LoRA rank 16 is a reasonable default for this narrow intervention. The small
dataset makes overfitting and generic response-style drift more immediate concerns
than adapter capacity. A useful initial configuration is rank 16, alpha 32,
dropout 0.05, two or three epochs, and checkpoints at least once per epoch, with a
matched base-model evaluation and non-ecological controls retained throughout.

## Clarification of R1 terminology

The initial planning discussion incorrectly interpreted “R1 answer” as a response
generated by DeepSeek-R1. The intended meaning is the H4rmony dataset's rank-1
completion: the most environmentally aligned of the three authored responses for
each prompt. The estimates and assumptions above have been corrected accordingly.

## Qwen3-8B R1-only SFT workflow implementation

The former Colab entry point for evaluating the released Flan-T5 H4rmoniousCaramel
checkpoint was replaced with an A100 workflow that fine-tunes `Qwen/Qwen3-8B` on
the H4rmony R1 answers. The notebook now contains only repository setup, Google
Drive mounting, a visible configuration, one reusable training call, and result
display. Data selection, tokenization, training, evaluation, and persistence are
implemented under `scripts/harmony_sft/`.

The current Hugging Face viewer for `neovalle/H4rmony` reports 2,016 pairwise rows
and a `PromptID` range from 1 through 677. This supersedes the earlier
517-row/512-prompt planning note, which described the older public GitHub training
CSV inspected at that time.
The implemented loader uses the current Hugging Face dataset, resolves its requested
revision to an immutable commit before loading, and records the exact count in the
run manifest. It groups by `PromptID`, selects `BetterCompletion` only from R1-R2
and R1-R3 rows, requires duplicated R1 values to agree, and retains one example per
prompt ID. It does not deduplicate distinct prompt IDs merely because their prompt
text matches; duplicate prompt text is instead counted in the manifest. R2-R3 rows
are never used as R1 supervision.

The default intervention is `Qwen/Qwen3-8B`, BF16, LoRA over all linear layers,
rank 16, alpha 32, dropout 0.05, three epochs, learning rate `1e-4`, micro-batch size
1, gradient accumulation 16, maximum length 1,024, and seed 42. Qwen's chat template
is applied with `enable_thinking=False`. Prompt tokens are labeled `-100`; only the
R1 answer and its EOS token contribute to the loss. If an example is too long, only
the left side of the prompt is truncated; the complete answer is retained.

Each run resolves immutable model and dataset revisions and writes directly under
`/content/drive/MyDrive/value-misalignment/harmony_r1_qwen3_8b/`. Persisted artifacts
include the exact selected examples and token-length manifest, resumable epoch
checkpoints, the final LoRA adapter and tokenizer, training metrics and log history,
matched base-versus-adapter raw scores, monotone threshold comparisons, response
curves, environment and hardware metadata, and hashes. `COMPLETE.json` is created
only after the final adapter, a resumable checkpoint, and required results have
been verified; exceptions create `FAILED.json` in the run directory.

The matched evaluation reuses the four ecological cost templates and exact Yes/No
sequence scoring from `scripts/harmony_eval/`, with thinking disabled for both the
base and adapted model. It evaluates the base before attaching LoRA and the trained
adapter in memory afterward, avoiding a second 8B model load. These templates are
still an exploratory screen, not a confirmatory generalization test.

No GPU training was run in the local development environment, so there is not yet
an observed SFT checkpoint, loss, runtime, or post-SFT effect. Static compilation
and all 33 local unit tests passed, including new tests for R1 extraction,
conflicting-source rejection, response-only masking, prompt-only truncation,
non-thinking Qwen formatting, configuration validation, and required resumable
checkpoint artifacts. The next step is to run the revised notebook on a Colab A100
and use the resulting Drive manifest to
replace the provisional runtime and dataset-length estimates with measured values.

## First Colab run: inconsistent R1 source records

The first attempted Colab run stopped during dataset preparation, before tokenizer
or model loading. For `PromptID` 131, the H4rmony R1-R2 and R1-R3 rows supply two
different `BetterCompletion` values even though both rows label that value R1:

- “Overfishing stresses the necessity for harmony in our relationship with the
  marine world, ensuring abundance for all future generations.”
- “Sustainable fishing practices have implications for global food security and
  socio-cultural dynamics.”

The original loader deliberately rejected this disagreement rather than silently
training on an arbitrary answer. The revised loader now treats the first,
explicitly ecolinguistics-aware answer as the known correction for PromptID 131,
consistent with the dataset's definition of R1. For any other disagreement, it
uses the assignments across R1-R2, R1-R3, and R2-R3 to prefer a candidate that is
not also assigned a lower rank. If that evidence is tied, the R1-R2
`BetterCompletion` is the workflow's canonical fallback.

This resolution is auditable rather than silent. Every selected example records
whether its R1 sources conflicted, the source answers, all candidate rank
assignments, and the selection method. The persisted `dataset/manifest.json`
records the total conflict count, method counts, and full conflict details. The
runner also prints the number of resolved records before tokenization.

All 36 local unit tests pass after the change. Regression coverage includes the
exact PromptID 131 defect, generic cross-pair rank resolution, the canonical
R1-R2 fallback, rejection of multiple answers within one canonical comparison,
and the existing response-only SFT and Drive-artifact checks. The failed Drive run
is not resumable because training never began; rerunning after updating the
repository should create a fresh timestamped run directory.
